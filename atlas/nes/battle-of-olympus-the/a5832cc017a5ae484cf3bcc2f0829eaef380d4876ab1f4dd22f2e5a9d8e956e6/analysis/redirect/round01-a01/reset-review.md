# Mirrored reset structure review

Claim: for each 16 KiB bank0..6, physical `16+bank*16384+$3FDA..+$3FE0` is an exact six-byte reset template `EE FB FF 4C 02 C0`. The first three bytes are proposed Observed Code; the last three are proposed Static Data representing the stored duplicate continuation instruction image. CPU origins are $FFDA and $FFDD; first-instruction observed contexts are `[0,1,2*bank,2*bank+1]`. The final-bank counterpart remains previously accepted Code.

Independent evidence: all eight complete templates are identical; each bank's reset/IRQ vector encodes $FFDA; each template is independently bounded by an inspected uniform FF prefix and the same cartridge trailer. `residual-and-reset.json` retains exact bytes/vector records. `reset-mapping-tests3.json` records executed RAM code that selects MMC1 mode2 and each upper bank, then jumps to $FFDA. Actual accepted fetches identify all seven INC storage origins. The INC changes the effective upper mapping; the next $FFDD fetch is physical $1FFED in the final bank. Trace aggregates survive snapshot imports; use the unique physical/context records, not per-run count totals.

The initial short test spent its budget inside an interrupt, so it did not test the mapper hypothesis. The successful method executes SEI/STA $2000 from RAM and allows 2,000 operations, with exact patches retained in `reset_probe3.py`. The RAM program is debugger-created; it proves neither immutable upload origin nor natural reset reachability.

The strongest alternative is Static Code for every copied JMP image. Template/vector/boundary evidence strongly supports the instruction-image role; missing local fetch alone does not reject that interpretation. A continuous physical same-copy INC/JMP claim is false because the mapper switches before JMP. The data proposal records the storage role without inventing a post-reset effective execution view for that physical copy. It does not call the suffix unused or dead. Independent disassembly may adopt a stronger Code-image representation if its views and mapper transition remain faithful; either decision must retain the copy relationship and separate actual fetch provenance. No ROM completion or full hardware compatibility claim follows.
