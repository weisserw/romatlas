# Revised compaction contract: active research

Target: bank 6/7 routine $8BCB..$8C81, then saved-selector refresh $E7A5/$E79B/$E762. Earlier return proof stopped at E9FD indirect writes and correctly identified that mutable count zero can make the scanner cover more than six records. The local $8C1D proposal did not establish a global return.

Changed inference: a meaningful **nonterminal party** precondition can prove the count never reaches zero. Let N = entry MutablePartyCount, with 1 <= N <= ActivePartyCount <= 6, and require at least one of the first N F785 records to have status & $0C == 0. One pass removes at most one marked record. The 43*(5-X) copy shifts later physical records left, and restores the removed record at ActivePartyCount-1, outside the new effective prefix because ActivePartyCount >= original N. Thus an unmarked record remains in the effective prefix, MutablePartyCount remains at least one, and every scanned/copied pointer stays in the six established RAM records. X==5 removes only the final marked slot and skips copying. The pass counter is initialized to N and decremented once per pass; it is not reset on the loop backedge.

This is an actual narrower contract, not an assumption that all game states are safe. The all-marked/zero-count cases remain outside it. Natural callers need not be proved for a structural conditional routine claim; don't promote this to an unconditional summary. For E7A5, preserve the separate ActivePartyCount/PartyCount relation and whether the preliminary status normalization and detail-panel callees preserve the invariant. For E762, its choice of PartyCount versus BattlePartyCount supplies another explicit precondition.

Next bounded action: inspect the exact primary compaction/copy/ECBC instructions and the detail-panel callee's memory footprint, then validate the finite control cases using a local static CPU model if available. Status-mask patterns are a finite algorithmic proof domain, not arbitrary gameplay RAM exploration. A useful result must establish pointer/count/stack preservation, not merely show a few successful executions. Stop this method if record restoration can put marked data back inside the effective prefix, a helper changes a count/pointer, or the proposed precondition does not support the full conditional return. ## Count-counter correction after the first finite check

The first 438-case immutable-instruction check passed (max 8,293 instructions), including exact record preservation under ActiveCount >= N and at least one survivor. It revealed that the survivor premise was stronger than needed for bank/stack return.

At scan-pass entry, **MutableCount >= RemainingPassCount >= 1**. Both start at N. A pass removes at most one record, while every pass decrements RemainingPassCount exactly once. Therefore the inequality persists at the next scan entry. If a removal makes MutableCount zero, RemainingPassCount becomes zero at the same pass end and the routine returns before any zero-count scan. The old all-marked objection was a sufficiency judgment on a possible local count value, not an observed counterexample to the complete two-counter algorithm.

For the bank-preserving return claim, initial 1 <= MutableCount <= 6 and 1 <= ActiveCount <= 6 suffice; ActiveCount >= N is needed for the stronger functional stable-compaction result, not for safe RAM destinations or balanced return. All-marked status patterns are allowed. The revised finite check covers all 1,512 combinations of N, ActiveCount, status-mask branch patterns and battle-layout flag, and asserts the count-counter inequality at actual $8BD0 scan entries. Standalone N=0 is still excluded; upstream ActiveCount=0 skip behavior must be checked separately.
